# Общие курсы, CSV и email

## Управление курсами

`POST /api/courses` и `PATCH /api/courses/{id}` принимают необязательный `cohortIds: string[]`.
Отсутствие поля сохраняет прежние назначения; пустой список снимает назначения. Повторы удаляются.
Не более 200 групп; проверяется принадлежность групп организации текущего пользователя.
Менять назначения могут администратор и организатор, преподаватель — только содержание своего курса.
Списки групп и их `courseIds` доступны через существующий `GET /api/cohorts`.

Связь many-to-many `CohortCourses` уже существовала: новая таблица и перенос назначений не требуются.
Состав курса хранится в единственном экземпляре. Доступ, прогресс и оценки используют прежние идентификаторы.
Снятие назначения закрывает доступ студентов группы, сохраняя их результаты обучения.
Демо поддерживает тот же выбор групп.

## CSV

Администратор: **Пользователи → Импорт из CSV**. Только режим «Сервер».
Файл UTF-8 (в том числе BOM), разделитель `,` или `;`, кавычки и удвоенные кавычки по RFC 4180.
До 1 МБ, 1000 пользователей, 50 колонок, 1000 символов в поле. Обязательные поля — `name`, `email`.
Поля `group`, `faculty` необязательны; произвольные заголовки сопоставляются перед проверкой.
CSV с синтаксически незакрытой кавычкой отклоняется целиком: надёжно восстановить границы строк невозможно.
Ошибки значений отдельных строк отражаются в отчёте, корректные строки обрабатываются.

```csv
name;email;group;faculty
Иван Примеров;ivan@example.org;М1227;ИНЭК
Анна Примерова;anna@example.org;М1227;ИНЭК
```

Группа должна существовать. Общий выбор группы в форме имеет приоритет над CSV.
Новая учётная запись всегда студент. Колонки роли и пароля не принимаются в mapping.
Проверка почты без учёта регистра; первый корректный экземпляр строки обрабатывается, остальные пропускаются.
По умолчанию существующие пользователи пропускаются. Опция изменения группы переводит существующего
активного студента в указанную группу, сохраняя имя, email, факультет, роль и результаты.
Модель пользователя остаётся прежней: **одна учебная группа у студента**.

`POST /api/users/import/preview` — проверка и отчёт без изменения данных.
`POST /api/users/import` — выполнение. Тело:

```json
{
  "requestId": "41586721-9d3c-4568-becf-b5a649c28cc0",
  "csv": "name,email\nИван Примеров,ivan@example.org",
  "columns": { "name": 0, "email": 1 },
  "group": "М1227",
  "updateExisting": false,
  "sendInvitations": true
}
```

Ответ: `created`, `updated`, `skipped`, `errors`, `rows[]` (номер записи с заголовком = 1,
имя, почта, группа, статус, ошибка). При предпросмотре счётчики описывают ожидаемое действие.
Повтор того же `requestId` возвращает сохранённый отчёт. Другое содержимое с тем же id — 409.
Повтор файла с новым id не создаёт дубликаты благодаря уникальному нормализованному email.
Импорты сериализованы блокировкой PostgreSQL; конкурентная регистрация той же почты пропускает строку
через savepoint, сохраняя другие строки. Группы блокируются на время обработки.
Шаблон и отчёт скачиваются из интерфейса; формулы CSV экранируются при экспорте.

Новые аккаунты получают хеш неизвестного случайного пароля, пароль не показывается и не сохраняется открытым.
Ссылки активации случайные (256 бит), в БД только SHA-256; тело приглашения в очереди зашифровано.
Ссылка действует 48 часов, секрет хранится во фрагменте URL (не передаётся в HTTP-запросе страницы).
`POST /api/auth/activate {token,password}` устанавливает пароль и отзывает все активации и сессии аккаунта.
Смена email/пароля, блокировка и административный сброс отзывают старые ссылки.
При отключённой отправке импорт создаёт аккаунты без доступного пароля: позже пригласите их через рассылки.

## SMTP

1. Обновить `.env`: `MAIL_PUBLIC_URL=https://edu.example.org` — адрес платформы для приглашений.
2. Применить миграции и пересобрать API: `docker compose --profile backend up -d --build db storage api`.
3. Администратор открывает **Рассылки и уведомления → Настройки SMTP**.
4. Заполнить Host, Port, Username, Password, email и имя отправителя. Выбрать STARTTLS (обычно 587)
   или SSL/TLS (обычно 465). Проверка сертификата обязательна, переход к незашифрованному соединению запрещён.
5. Сохранить, проверить подключение, отправить тестовое письмо на свой адрес.
6. Включить нужные автоматические события. По умолчанию приветствие/группа/курс выключены,
   приглашение нового пользователя включено. Ручные приглашения и флажок импорта — явный выбор администратора.

Настройки хранятся в PostgreSQL. Пароль защищён ASP.NET Data Protection, API возвращает только `hasPassword`.
Пустой пароль в форме сохраняет прежний. Пароль и SMTP-тексты исключений не записываются в журнал.
Ключи — постоянный Docker volume `mail_keys`, каталог `/var/helios-mail-keys`, принадлежит пользователю API.
Резервная копия должна включать БД **и ключи**; потеря ключей делает SMTP-пароль и тела очереди нечитаемыми.
Доступ к каталогу ключей ограничьте учётной записью сервиса и администраторами сервера.
При нескольких экземплярах API каталог ключей должен быть общим. Не публикуйте его в репозитории.

Без Docker: `Mail__PublicUrl`, `Mail__KeyDirectory`; строка PostgreSQL — существующая `ConnectionStrings__Database`.
Незашифрованный SMTP возможен только при явном `Mail__AllowInsecure=true` для локального тестового сервера.
В production эта настройка не требуется. SMTP не задаётся в переменных браузера.

## API почты

Все `/api/mail/*` — только администратору (`system.manage`), с серверной сессией и защитой от чужого Origin.
Пользователь и организация берутся из сессии. Новые ответы включены в OpenAPI и сгенерированные типы.

| Метод и путь | Действие |
| --- | --- |
| `GET /api/mail/settings` | Настройки без секрета и состояние проверки |
| `PUT /api/mail/settings` | SMTP и флаги событий; пароль необязателен |
| `POST /api/mail/check` | `{}` — подключение и авторизация; `{email}` — тестовое письмо |
| `POST /api/mail/audience` | `{userIds?,cohortIds?,all?}` → `{count}` |
| `POST /api/mail/campaigns` | Постановка рассылки в очередь |
| `GET /api/mail/campaigns` | Последние 100 рассылок со счётчиками |
| `GET /api/mail/campaigns/{id}` | Получатели, статусы, попытки и безопасные ошибки |
| `POST /api/mail/invite/{id}` | Одноразовое приглашение активному пользователю |

Рассылка: `{requestId: UUID, audience: {userIds?,cohortIds?,all?}, subject, text, html?, confirmAll?}`.
Обязательна текстовая версия. HTML предпросмотр изолирован в iframe без скриптов и внешних ресурсов.
Для `all=true` обязательно `confirmAll=true`. До 10000 активных получателей за операцию.
Почта нормализуется, повторяющиеся получатели исключаются. Заблокированные/удалённые не получают письма.
Перед SMTP повторно проверяются статус аккаунта и соответствие email снимку рассылки.

Запросы отправки, проверки, импорта и приглашения ограничены 20 операциями в минуту на администратора.
При 20000 ожидающих писем создание очередной ручной рассылки блокируется (429).
Тот же идентификатор рассылки и содержание возвращают прежнюю операцию; иное содержание — 409.
Повторное приглашение до истечения срока блокируется; после окончательной ошибки предыдущей отправки
администратор может явно отправить новое, отозвав старую ссылку.

## Очередь и события

`MailCampaign` + `MailRecipient` — сохраняемая очередь PostgreSQL; запись письма и бизнес-изменение в одной транзакции.
Фоновый worker — один отправитель на БД благодаря advisory lock, не чаще одного письма в секунду.
Временные отказы SMTP 4xx и ошибки подключения — до трёх попыток с паузами 30 и 60 секунд.
Одна попытка ограничена 15 секундами. Постоянные отказы сразу завершаются ошибкой.
Статусы: `queued`, `running`, `completed`, `partial`, `failed`; счётчики `total/sent/failed/pending`.
Состояния получателя: `queued`, `sending`, `sent`, `failed`.
**`sent` означает приём SMTP, доставка в почтовый ящик не подтверждается.**

После обрыва в стадии `sending` результат помечается неизвестным/ошибочным и автоматически не повторяется:
SMTP не предоставляет гарантию exactly-once, а повтор мог бы создать дубликат. После проверки журнала
почтового сервера администратор может создать новую рассылку явно.
Миграции и начальное наполнение не отправляют почту. Повтор уже выполненного импорта/рассылки не создаёт событий.
Изменение группы на прежнее значение и сохранение прежних назначений курса также не создают писем.
События: создание аккаунта, приглашение, группа, назначение курса, публикация курса.
При одновременной публикации и смене групп учитывается окончательный состав назначений.

Миграция `20261113124812_BulkImportAndMail` только добавляет пять таблиц:
`MailSettings`, `MailCampaign`, `MailRecipient`, `AccountActivation`, `UserImport`.
Уникальные ограничения защищают повторные операции и получателей. Старые учебные таблицы и связи не меняются.

## Проверки и границы

- `npm run check`, `npm run build` (в Linux Docker при недоступности шрифтов/сбое Turbopack на Windows).
- `npm run test:backend` подключает `compose.testing.yaml`, в CI тот же профиль.
- `backend/tests/bulk-mail.test.mjs` поднимает локальный SMTP на 2525 без внешних писем; проверяет права,
  три группы, общий курс, CSV/повторы/частичные ошибки, активацию, скрытие секрета, дедупликацию, ошибки и повтор SMTP,
  автоматические события и отзыв ссылок. Нужен доступ контейнера к `host.docker.internal`.
- Реальный почтовый провайдер, DNS/SPF/DKIM/DMARC, папка «Спам» и доставка проверяются после настройки владельцем.
- История в интерфейсе ограничена последними 100 рассылками; в БД сохраняется целиком.
- Автоматического повторного запуска неясной отправки нет; редактирования уже запущенной рассылки нет.
- Импорт и почта в демо показывают «Доступно в режиме „Сервер“».
