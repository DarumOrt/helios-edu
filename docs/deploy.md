# Выкладка на сервер

Как HeliosEDU ставится на рабочий сервер и обновляется. Первая часть — для нас (сервер Timeweb, `heliosedu.ru`),
вторая — для образовательной организации, которая ставит платформу у себя. План и решения — [modules/deploy.md](modules/deploy.md).

## Как это устроено

```
интернет ──► Caddy (80/443, HTTPS) ──► сайт (Next) ──► API (C#) ──► база (PostgreSQL)
                    └── files.… ──────► хранилище файлов (SeaweedFS)
```

- Наружу открыт только Caddy. Сайт, API, база и хранилище видны только внутри Docker.
- Сайт и файлы — на двух адресах одного домена: `heliosedu.ru` и `files.heliosedu.ru`. Файлы браузер берёт
  прямо из хранилища по временным ссылкам; отдельный адрес нужен, чтобы файл студента не считался частью сайта.
- Образы сайта и API собирает GitHub Actions и кладёт в GHCR. Сервер их только скачивает.
- На сервере лежит папка `/opt/heliosedu`: `compose.prod.yaml`, `Caddyfile`, `scripts/server/` (их каждый раз
  привозит выкладка — руками не править), `.env` (настройки и пароли, заполняется один раз) и `.version`.
- База чистая: без демо-курсов и демо-пользователей. Первого администратора создаёт сервер из `.env`;
  остальных заводит администратор (в том числе импортом CSV).

## Выкладка и откат — кнопкой

GitHub → **Actions → «Выкладка на сервер» → Run workflow** (ветка `main`):

| Поле | Что писать |
| --- | --- |
| Номер версии | три числа через точку: `0.1.0`, следующая — `0.1.1`, `0.2.0`… Номер нельзя использовать дважды |
| Собрать образы | включено — обычная выкладка; выключено — откат на уже собранную версию |

Что происходит: сборка образов → копия базы на сервере → новые образы → запуск → проверка, что сайт и API отвечают.
Если версия не поднялась, выкладка краснеет и в журнале видны последние строки сервера.

**Откат:** тот же запуск с прежним номером и выключенной сборкой. Важно: код возвращается, а база — нет.
Если новая версия успела изменить структуру базы, после отката восстановите копию, снятую перед выкладкой
(«Восстановление» ниже).

## Первая установка (один раз)

1. **Сервер:** Ubuntu 24.04, 2 ядра / 4 ГБ / от 50 ГБ, Docker с плагином compose. Отдельный пользователь для выкладки
   (в группе `docker`), вход по SSH-ключу, сетевой экран: открыты 22, 80, 443.
2. **Домен:** записи `A` для `heliosedu.ru` и `files.heliosedu.ru` → адрес сервера. Без них Caddy не получит сертификат.
3. **Папка и настройки** на сервере:

   ```bash
   sudo mkdir -p /opt/heliosedu /var/backups/heliosedu
   sudo chown "$USER" /opt/heliosedu /var/backups/heliosedu
   ```

   Скопировать [.env.prod.example](../.env.prod.example) в `/opt/heliosedu/.env`, заполнить адреса, три пароля
   (`openssl rand -hex 24` на каждый) и первого администратора. Закрыть файл: `chmod 600 /opt/heliosedu/.env`.
4. **Секреты в GitHub** (Settings → Environments → `production`):

   | Секрет | Значение |
   | --- | --- |
   | `DEPLOY_HOST` | адрес сервера |
   | `DEPLOY_USER` | пользователь для выкладки |
   | `DEPLOY_SSH_KEY` | закрытый ключ, созданный только для выкладки (не личный) |
   | `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan <адрес сервера>` — чтобы выкладка не попала на чужой сервер |

   Там же можно включить «Required reviewers»: тогда выкладку подтверждает человек.
5. **Первая выкладка** — кнопкой, версия `0.1.0`. После неё: войти администратором из `.env`, сменить пароль
   (сайт попросит сам), стереть `ADMIN_EMAIL` и `ADMIN_PASSWORD` из `.env`.
6. **Почта:** SMTP настраивает администратор в интерфейсе («Настройки»). Для своего домена нужны записи SPF и DKIM.
7. **Копии по расписанию** — см. ниже.

## Копии

`bash /opt/heliosedu/scripts/server/backup.sh` складывает в `/var/backups/heliosedu/<дата-время>/`:

| Файл | Что это |
| --- | --- |
| `db.dump` | база (пользователи, курсы, оценки, журнал) |
| `mail-keys.tar` | ключи почты: без них пароль SMTP и письма в очереди из базы не прочитать |
| `storage.tar` | файлы курсов и работ студентов |
| `version.txt` | версия сайта, на которой снята копия |

- Полная копия на время копирования файлов останавливает хранилище (видео и файлы недоступны — минуты),
  поэтому её делаем ночью. С ключом `--no-files` — только база и ключи, без остановки: так делает выкладка.
- Каждую ночь, в 03:00 по времени сервера — строка в `crontab -e` пользователя выкладки:

  ```
  0 3 * * * bash /opt/heliosedu/scripts/server/backup.sh >> /var/backups/heliosedu/backup.log 2>&1
  ```

- На сервере хранится 14 дней (`BACKUP_KEEP_DAYS`).
- **Копия на том же сервере не спасает, если пропал сервер.** В `.env` задаётся `BACKUP_UPLOAD_CMD` — команда,
  которая получает путь к готовой копии и уносит её (например, скрипт с `rclone copy` в S3-хранилище Timeweb
  или на другой сервер). Куда именно — решим при настройке сервера.

### Восстановление

```bash
bash /opt/heliosedu/scripts/server/restore.sh /var/backups/heliosedu/20261114-030000 --yes
```

Текущие данные заменяются данными копии. Версия сайта должна совпадать с `version.txt` копии: если нет — сначала
выкладка этой версии (с выключенной сборкой), потом восстановление. Копия без `storage.tar` файлы не трогает.
На новом сервере: «Первая установка» (с тем же `.env`) → выкладка версии из копии → восстановление.

## Что проверить после выкладки

- `https://heliosedu.ru` открывается, замок HTTPS, вход работает.
- Загрузка файла в курс и его просмотр (это путь через `files.heliosedu.ru`).
- На сервере: `bash /opt/heliosedu/scripts/server/compose.sh ps` — все пять служб работают;
  журнал — `… compose.sh logs --tail 100 api`.

## Для организации: установка у себя

Нужны: сервер с Linux и Docker, домен с двумя именами (сайт и файлы), почтовый ящик с SMTP.
Организация — оператор персональных данных своих пользователей.

1. Сделать копию (fork) репозитория — образы соберутся в GHCR организации, адрес подставится сам.
2. Выполнить «Первую установку» со своими адресами в `.env` и своими секретами в GitHub.
3. Название организации, факультеты и группы задаются в интерфейсе администратором.

Без GitHub Actions: собрать образы самим (`docker build -t <реестр>/helios-edu-web:<версия> .` и
`docker build -t <реестр>/helios-edu-api:<версия> ./backend`), положить в свой реестр, скопировать на сервер
`compose.prod.yaml`, `Caddyfile`, `scripts/server/` и запустить
`HELIOS_IMAGES=<реестр>/helios-edu bash scripts/server/deploy.sh <версия>`.

### За Nginx организации

Если 80 и 443 на сервере уже занимает Nginx организации, HTTPS остаётся на нём, а Caddy слушает только локально.
В `.env`:

```
CADDY_SITE_ADDRESS=http://lms.example.org
CADDY_FILES_ADDRESS=http://files.lms.example.org
HTTP_BIND=127.0.0.1:8081
HTTPS_BIND=127.0.0.1:8444
TRUSTED_PROXIES=private_ranges
```

`SITE_URL` и `FILES_URL` остаются с `https://`. В Nginx для обоих имён:

```nginx
location / {
    proxy_pass http://127.0.0.1:8081;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto https;
    client_max_body_size 1100m;   # видео до 1 ГБ
    proxy_request_buffering off;
}
```

Этот вариант описан, но на настоящем сервере ещё не проверен.

## Настройки, которые отличают рабочий сервер от локального

| Что | Где | Зачем |
| --- | --- | --- |
| Защищённые cookie | нет `Auth__AllowInsecureCookies` | сессия передаётся только по HTTPS |
| `DEMO_MODE=off` | сайт | переключателя «Демо» нет, только настоящие данные |
| нет `Database__SeedDemoData` | API | чистая база |
| `Admin__Email`, `Admin__Password` | API | первый администратор, пока в базе нет ни одного |
| `TRUSTED_PROXY=on` и `Auth__TrustClientAddressHeader=true` | сайт и API | лимит входов считается по адресу пользователя: Caddy пишет его в `X-Real-IP`, сайт передаёт API. Включать только когда сайт и API закрыты от интернета — иначе адрес можно подделать |
